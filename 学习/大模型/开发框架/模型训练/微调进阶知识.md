# 1 基础
## 1.1 thinking 是什么？
### 1.1.1 常见训练方法：
- a. 监督微调（Supervised Fine-Tuning）
    - 收集带有 **思考链** 的数据（如链式推理解析题）
		```shell
		问题：<Question>
		思考链：
		Step 1 ...
		Step 2 ...
		最终答案：<Answer>
		
		```

- b. Prompt Engineering（提示工程）
	```python
	Let's think step by step.
	```

- c. 少样本学习 + CoT

- d. 强化学习（Reinforcement Learning）
	- 引入奖励机制：推理路径正确 → 给奖励
	- 常见 RLHF（人类反馈强化学习）：让人类评价模型的推理质量和答案质量。

### 1.1.2 训练数据
为了训练 thinking：
- **数据必须包含“推理过程”而不仅是答案**  
    如果只给答案，模型只能死记结果，不会学到推理方法。
- 推理过程要清晰、结构化（Step-by-step）
- 答案和推理过程要严格对应，不能乱跳逻辑

```json
[
  {
    "instruction": "请计算：25 × 4 + 15，并给出详细推理过程。",
    "input": "",
    "output": "Step 1: 首先计算 25 × 4 = 100。\nStep 2: 然后再计算 100 + 15 = 115。\n最终答案：115"
  },
  {
    "instruction": "李雷从家到学校要走 3 公里，他每天上学和放学各走一次。一周有5天上学。他一周总共走多少公里？请一步步推理。",
    "input": "",
    "output": "Step 1: 每天上学走 3 公里，放学走 3 公里，总共 3 + 3 = 6 公里。\nStep 2: 一周上学 5 天，总共走 6 × 5 = 30 公里。\n最终答案：30 公里"
  },
  {
    "instruction": "已知小明比小红高5厘米，小红身高为160厘米，请一步步推理小明身高。",
    "input": "",
    "output": "Step 1: 小红身高 160 厘米。\nStep 2: 小明比小红高 5 厘米，所以小明 = 160 + 5 = 165 厘米。\n最终答案：165 厘米"
  }
]
```

**混合训练数据**

不要全是 CoT 格式，要在训练集中加入：
- **普通直接回答格式**（QA、闲聊、事实查询）
- **CoT 格式**（需要推理的任务）
- **多种任务形式**（数学、逻辑、推理问答、开放性讨论）

这样模型会学到情境判断：
> “需要推理时用思维链，不需要推理时直接输出答案”。

比例建议：
- **推理任务**占 30%-50%
- **直接回答任务**占 50%-70%


## 1.2 Pre-training, SFT (Supervised Fine-tuning), RLHF 三个阶段的目标和数据差异是什么？
| 阶段                | 主要目标                    | 数据特点                          | 模型能力变化             |
|-------------------|-------------------------|-------------------------------|--------------------|
| Pre-training（预训练） | 学会语言基础 & 通用知识           | 规模极大（数十亿~数万亿 token），多为爬取的原始文本 | 从零到能理解和生成语言        |
| SFT（监督微调）         | 学会遵循指令、格式化输出            | 高质量、人工标注、指令+输出对               | 从通用“语言生成”到能做具体任务   |
| RLHF（人类反馈强化学习）    | 优化输出质量、提升对齐性（Alignment） | 人类评价数据 / 排序数据                 | 从“能执行任务”到 “符合人类偏好” |

### 1.2.1 **阶段 1：Pre-training（预训练）**

- **目标**：
    - 让模型学会语言模式（语法、语义）
    - 获取广泛的知识储备
    - 建立 token 预测能力
- **数据**：
    - 大规模原始文本（书籍、网页、维基、新闻、代码等）
    - 不需要人工标注
- **训练方式**：
    - 通常是语言模型任务：
        - _Encoder-only_：Masked Language Model（BERT）
        - _Decoder-only_：Next Token Prediction（GPT）
    - 损失函数多是交叉熵
- **缺点**：
    - 只能模仿训练文本的语言风格，没有任务执行能力
    - 用户问指令类问题时，模型可能不知道该怎么输出

---

### 1.2.2 **阶段 2：SFT（Supervised Fine-Tuning，监督微调）**

- **目标**：
    - 教模型按照给定指令执行任务
    - 学会特定输出格式、任务流程
- **数据**：
    - 高质量指令数据（Instruction Tuning）
    - 人工编写的 **输入 → 输出** 对
    - 覆盖多种任务：问答、推理、翻译、摘要、代码生成等
- **训练方式**：
    - 依然是监督学习（交叉熵），但数据是人工标的目标输出
    - 模型在这个阶段学会“指令-响应”模式
- **缺点**：
    - 输出只是模仿训练数据，不一定能完全匹配人类偏好
    - 如果数据质量低，可能学到错误模式

---

### 1.2.3 **阶段 3：RLHF（Reinforcement Learning with Human Feedback）**

- **目标**：
    - 对齐（Alignment）：让模型的回复更符合人类偏好、安全规范
    - 优化多个可能回答中的最佳答案选择能力
- **数据**：
    - 人类评价数据（Human Preference data）
        - 给模型一个问题，让它生成多个回答
        - 人类排序（最好→最差）
    - 这些排序数据用来训练一个 **奖励模型（Reward Model）**
- **训练方式**：
    - 两步：
        1. **奖励模型训练**：根据人类排序学会评估回答质量
        2. **强化学习**（PPO 等）：用奖励模型指导 LLM 输出更优回答
- **效果**：
    - 回复更贴近人类风格
    - 避免违背安全策略
    - 更温和、友好、可控

---

### 1.2.4 **核心区别总结**

|阶段|模型状态|数据来源|任务类型|
|---|---|---|---|
|Pre-training|学语言 + 知识|大规模网络文本（无标注）|通用语言建模|
|SFT|学任务执行|人工编写指令数据（有标注）|问答、推理、格式化输出|
|RLHF|调人类偏好|人类排序/评分数据|优化生成质量和对齐性|

---

### 1.2.5 一个类比（更容易记）

- **Pre-training**：就像读遍各种书、新闻、网页，获取百科知识
- **SFT**：就像参加培训班，学习按老师要求完成作业
- **RLHF**：就像让老师对作业打分，再根据评分优化写作风格和质量



## 1.3 Scaling Laws 

### 1.3.1 原理
**规模定律**
Scaling Laws 指的是大模型性能（例如损失值、准确率）与 **模型规模、数据规模、计算量** 等之间的数学规律。  
它告诉我们：如果模型更大、数据更多、训练计算更多，性能会如何变化。


**核心思想**：
- 模型性能随规模提升，呈现近似幂律关系（power law）
- 损失值（Loss）随数据量/模型参数规模增加而下降，但会趋近于某个最小值（平滑曲线）

**典型公式**
对于自回归语言模型，大致有：  
$$L(N)≈L_{∞}+k⋅N^{−α}$$
- L(N)：损失值（Loss）
- N：训练数据规模（token 数）
- L∞​：损失值的理论下限
- k,α：拟合出来的常数

**关键规律**
1. **模型参数增加 → 性能提升**（但计算成本也线性增加）
2. **数据量增加 → 性能提升**（但存在饱和点）
3. **计算量增加 → 性能提升**（但要与参数规模匹配，否则浪费）


### 1.3.2 指导意义

虽然 Scaling Laws 多用于大规模预训练阶段，但它对 **微调** 有几个关键指导点：

- **匹配数据规模与模型规模**
	- 如果微调数据远小于模型需要的规模，容易 **过拟合** 或 **遗忘** 原有能力
	- Scaling Laws 告诉我们：应该根据模型参数数量，提供足够的数据量
	- Chinchilla规律：参数太大、数据太少 → 不划算，性能提升有限
	**实践建议**：
		 参数规模（百万级） → 微调数据至少数百万到上亿 token  
		 参数规模（十亿级） → 微调数据至少数亿 token，避免“硬塞少量数据”导致退化

- **计算资源与训练轮次**
	- Scaling Laws 反映了 **计算预算与性能提升的平衡点**
	- 微调阶段不必盲目增加训练步数，如果数据和计算不匹配，性能提升有限甚至过拟合

- **是否选择全量微调**
	- 对于超大模型，全量微调需要匹配 Scaling Laws 中建议的数据规模，否则容易浪费计算量
	- 如果微调数据不足 → 考虑 LoRA、Adapter、Prefix Tuning 等参数高效方法，这样不用全量微调也能提升任务性能

- **任务难度与数据质量**
	- Scaling Laws 在预训练中是“**数量驱动**”，但在微调中，**数据质量**对性能提升更关键。  
	- 数量不足时，高质量数据可以部分弥补规模不足。

**数据量 要与 模型规模和计算预算相匹配**，否则要用参数高效微调方法来避免浪费资源和性能退化


## 1.4 BF 16 与  FP16
FP 16 的精度要高于BF 16

| 特性      | FP16         | BF16                   |
| ------- | ------------ | ---------------------- |
| 指数位     | 5 bits       | 8 bits（与 FP32相同）       |
| 尾数位     | 10 bits（精度高） | 7 bits（精度略低）           |
| 数值范围    | 小            | 大（与 FP32相同）            |
| 容易溢出/下溢 | 容易（范围窄）      | 不容易（范围宽）               |
| 硬件支持    | CUDA、部分 TPU  | TPU（原生）、NVIDIA Ampere+ |
|         |              |                        |
### 1.4.1 why BF 16?
- 数值范围更大，溢出更少
	- 大模型训练梯度范围很广，尤其是在深层网络或大 batch 时，FP16 的指数范围可能不够 → 会造成 **溢出**（Inf）或 **下溢**（变 0）。
	- BF16 的指数范围与 FP32相同，几乎不会溢出 → 更稳定。

-  不需要复杂的 **loss scaling**
	- FP16 常常要用 **loss scaling**（把损失乘一个大数以避免梯度下溢）
	- BF16 因为指数范围大，大部分情况不需要额外 scaling，简化训练流程。

- 性能与 FP16 接近
	- 在现代 GPU（如 NVIDIA A100、H100）或 TPU 上，BF16 的计算速度和 FP16差不多。
	- 显存占用也一样（都是 2 bytes）。

- 对大规模分布式训练更友好
	- 数值稳定性意味着跨数百甚至上千 GPU/TPU 同步时更少出错。
	- 大模型（数十亿~数千亿参数）训练时梯度波动很大，BF16 在这种场景更安全。

<font color="#00b050">FP16：数值范围小，精度高 → 更适合较小网络或推理（inference）场景</font>
<font color="#00b050">BF16：数值范围大，精度稍低 → 更适合深层、大模型训练，稳定性高</font>

## 1.6 SwiGLU 

大模型（如LLaMA、GPT系列、PaLM等）从ReLU转向SwiGLU，主要基于**数学表达能力和训练效率的显著提升.**

### 1.6.1 SwiGLU 
SwiGLU 是 **GLU（Gated Linear Unit）** 的一种变体，结合了 **Swish 激活函数**：

$$SwiGLU(x)=Swish(xW+b)⊗(xV+c)$$

其中：

- xx ：输入
- W,V：两个独立的权重矩阵（注意：**参数量翻倍**）
- ⊗ ：逐元素相乘（gating 机制）
- $Swish(z)=z⋅Sigmoid(βz)$ ，通常取 β=1 ，即 $Swish(z)=z⋅Sigmoid(z)$

> 📌 在实现中，常将 xW 和 xV 拼接后一次矩阵乘法完成，再 split。


### 1.6.2 why?
- 1) **更强的表达能力（Gating 机制）**
	- **ReLU**：只是简单地将负值置零，输出 = max⁡(0,x)
	- **SwiGLU**：引入 **门控（gating）** —— 一个分支（ Swish(xW) ）作为“门”，控制另一个分支（ xV ）的信息流。
	    这类似于 LSTM 中的 forget gate，允许模型**动态决定哪些信息保留、哪些抑制**，表达能力远超 ReLU。
> 💡 直观理解：ReLU 是“硬开关”，SwiGLU 是“软调光旋钮”。

- 2) **更平滑的梯度（无 dying ReLU 问题）**
    - **ReLU 的致命缺陷**：
        - 当输入 < 0 时，梯度 = 0 → **神经元“死亡”**，无法更新；
        - 在深层网络中，大量神经元可能永久失效。
    - **SwiGLU 的优势**：
        - Swish 函数处处可导，梯度平滑；
        - 即使输入为负，仍有非零梯度（因为 σ(z)>0 ）；
        - **训练更稳定，收敛更快**。

- 3)**实证性能显著提升（尤其在大模型上）**
	- **LLaMA (Meta)**
		- 明确说明：“SwiGLU 提升性能，尽管增加 2/3 参数”
	- **PaLM (Google)**
		- 在 540B 模型中使用，比 ReLU / GeLU 更优
	- **Qwen / DeepSeek / Mistral**
		- 全面采用
	- **Shazeer (2020) 原始论文**
		- GLU 变体, 在语言建模中，GLU > ReLU > tanh

> 📊 实验数据（来自 [Shazeer, 2020](https://arxiv.org/abs/2002.05202)）：
> - 在相同参数量下，**GLU-based 激活比 ReLU 降低 2–5% 的验证损失**；
> - 在大模型上，这种差距会被放大。

- (4) **对长序列和复杂推理更友好**
	- SwiGLU 的 gating 机制能更好地建模 **token 之间的依赖关系**；
	- 在需要多步推理的任务（如数学、代码）中，信息门控有助于**保留关键中间状态**。

### 1.6.3 SwiGLU的代价

| 缺点         | 说明                                     |
| ---------- | -------------------------------------- |
| 参数量增加 ~50% | 因为需要两个投影矩阵 W 和 V （但通常 FFN 维度会调整以平衡总参数） |
| 计算开销略高     | 多一次矩阵乘 + element-wise multiply         |
| 内存占用稍增     | 中间激活更多                                 |

但大模型开发者认为：**这点开销换来显著性能提升，完全值得**。
> 💡 例如 LLaMA 将 FFN 隐藏层维度从 4d 降到约 2.67d ，使得总参数量与 ReLU 版本相当，但性能更高。
---


| 原因       | 说明                         |
| -------- | -------------------------- |
| 更强建模能力   | 门控机制动态控制信息流                |
| 训练更稳定    | 无 dying neuron，梯度平滑        |
| 实证性能更高   | 在语言建模任务上 consistently SOTA |
| 大模型能承受开销 | 参数/计算增加 vs 性能收益，划算         |
| 社区共识形成   | LLaMA 等标杆模型采用，成为事实标准       |

## 1.7 RoPE
### 1.7.1 位置编码
想象一句话：
> “猫 追 老鼠”



模型看到的是三个词：`猫`、`追`、`老鼠`。  
但如果不告诉它顺序，它可能理解成“老鼠追猫”！

所以，我们需要给每个词**加上位置信息**，比如：

- `猫` → 位置 0
- `追` → 位置 1
- `老鼠` → 位置 2

传统方法（如 BERT）是直接加一个“位置向量”：
```
词向量 + 位置向量 = 带位置的向量
```

但这有个大问题：**如果训练时最长句子是 512 个词，测试时遇到 600 个词，模型就懵了！** —— 这叫**外推性差**。

### 1.7.2 RoPE 的核心思想：**用“旋转”表示位置**
RoPE 不再“加”位置，而是**把词向量“旋转”一个角度，角度由位置决定**。

### 1.7.3 比喻：钟表指针

想象每个词是一个**钟表指针**：

- 位置 0 → 指向 12 点（0°）
- 位置 1 → 指向 1 点（30°）
- 位置 2 → 指向 2 点（60°）
- ……

**词的内容 = 指针长度，位置 = 指针方向**。

这样，两个词的“相对位置”就变成了“**夹角**”！


假设一个词的向量是二维的（实际是高维，但原理一样）：

```
x = [x₁, x₂]
```

在位置 `m`，RoPE 把它变成：

```
f(x, m) = [ x₁·cos(mθ) - x₂·sin(mθ),  
            x₁·sin(mθ) + x₂·cos(mθ) ]
```

这其实是**把向量 (x₁, x₂) 绕原点逆时针旋转了 mθ 角度**！

> 📌 其中 θ 是一个预设的频率（比如 θ = 1/10000^(2i/d)），保证不同维度“转速”不同。

### 1.7.4 相对位置的优势


RoPE即具有**绝对位置**信息也包含了**相对位置信息**，但是在计算注意力机制的时候，关注的是其相对位置信息


**两个词的注意力得分，只和它们的相对位置有关！**
假设：
- 词 A 在位置 `m`
- 词 B 在位置 `n`

它们的注意力计算涉及内积：`f(x, m) · f(y, n)`
经过三角函数运算（略去推导），你会发现：

> **这个内积 = 一个只依赖于 (m - n) 的函数！**

也就是说：

- 模型看到“位置 10 和 15”的词对 → 相对位置 = 5
- 模型看到“位置 100 和 105”的词对 → 相对位置 = 5
- **它们的注意力得分是一样的！**

✅ 这就是 RoPE 的魔法：**天然编码了相对位置信息**！

### 1.7.5 外推性

传统位置编码（如正弦）在训练时只见过位置 0~512。  
当遇到位置 600 时，它的位置向量是“没见过的新东西”，模型不会处理。

但 RoPE 不同！
因为 RoPE 的旋转角度是**连续、平滑、周期性**的：

- 位置 512 的旋转角度 = 512θ
- 位置 600 的旋转角度 = 600θ

虽然 600θ 没见过，但它**只是比 512θ 多转了一圈多一点**，**数学性质完全一致**！

> 🌰 就像钟表：你见过 11 点，也能理解 13 点（= 1 点）—— 因为指针旋转是连续的！

所以，即使训练时最长 512，测试时 1000 也能 work！


| 问题          | RoPE 的答案                         |
| ----------- | -------------------------------- |
| 怎么加位置信息？    | 不加！把词向量“旋转”一个角度，角度 = 位置 × 频率     |
| 怎么知道两个词的距离？ | 它们的“夹角” = 相对位置！注意力自动算出来          |
| 为什么能处理更长文本？ | 旋转是平滑连续的，位置 1000 只是多转了几圈，数学规则不变！ |

## 1.8 Flash Attention
FlashAttention 是一种**I/O 感知（I/O-aware）的精确注意力机制算法**，由 Tri Dao 等人在 2022 年提出。
它的核心目标是**在不牺牲计算精度的前提下，显著降低显存占用并加速注意力计算**，尤其适用于长序列场景（如 8K、64K 甚至 100K tokens）。

### 1.8.1 传统 Attention 的瓶颈
标准自注意力公式为：
$$Attention(Q, K, V)=softmax(\frac{QK^T}{\sqrt{ d_{k} }})V $$

存在两大问题：
- 1. **显存复杂度高（O(N²)）**
	 - 需要显式生成并存储中间矩阵 $S=QK^T$ （大小 N×N ）。
	 - 对于 N=8192 ，单个 float16 的 S 矩阵就占：
	    8192×8192×2 bytes≈128 MB
	- 多头 + 批次 + 反向传播梯度 → 显存爆炸（常超 40–80 GB）。

- 2.  **I/O 瓶颈（Memory Wall）**
    - GPU 架构有两层内存：
        - **HBM（High Bandwidth Memory）**：容量大（40–80 GB），但带宽低（~1.5 TB/s）。
        - **SRAM（片上缓存，如 shared memory）**：容量极小（~200 KB/SM），但带宽极高（~19 TB/s）。
    - 标准 Attention 实现中：
        - 先算 $S=QK^T$→ 写入 HBM；
        - 读 $S$ → 算 softmax → 写回 HBM；
        - 读 softmax 结果 + V → 算输出 → 写 HBM。
    - GPU 的 HBM（高带宽内存）比片上 SRAM 慢 10–100 倍
    - 大量时间花在“搬运数据”，而非计算 → **访存密集型（Memory-Bound）**
- **频繁读写 HBM 成为性能瓶颈**，GPU 计算单元大量时间在“等数据”。

> 💡 关键洞察：**Attention 不是计算密集型，而是 I/O 密集型！**

### 1.8.2 attention 计算密集型、IO密集型？

**Attention（特别是解码阶段的Attention）本质上是I/O密集型而非计算密集型**

**计算强度 = FLOPs / 字节（内存访问量）**


```python
# 假设：d_model=4096, seq_len=1024, 单精度FP32
# 解码阶段生成一个token的Attention计算：

# A. 内存访问量（字节）
# 1. 读取KV Cache: 2 * layers * seq_len * d_model * 4字节
#    = 2 * 32 * 1024 * 4096 * 4 = 1 GB
# 乘2是因为一个K、一个V
# 2. 读写中间结果: ~100 MB
# 总内存访问: ~1.1 GB

# B. 计算量（FLOPs）
# 1. Q@K^T: seq_len * d_model * 2 = 1024 * 4096 * 2 = 8.4 MFLOPs
# 2. Softmax: ~3 * seq_len = 3 KFLOPs
# 3. 加权求和: seq_len * d_model * 2 = 8.4 MFLOPs
# 总计算量: ~16.8 MFLOPs

# C. 计算强度
计算强度 = 16.8e6 FLOPs / 1.1e9 字节 ≈ 0.015 FLOPs/byte

# D. 硬件能力对比
# 现代GPU（如A100）:
# - 峰值算力: 312 TFLOPS (FP16)
# - 内存带宽: 1.5 TB/s
# - 理论计算强度上限: 312e12 / 1.5e12 = 208 FLOPs/byte

# E. 结论
# Attention的计算强度(0.015) << 硬件能力(208)
# 差距: 4个数量级！
```


| 场景     | 序列长度 | 计算强度             | 瓶颈类型    | 证据              |
|--------|------|------------------|---------|-----------------|
| 短文本分类  | 512  | ~10 FLOPs/byte   | 轻度I/O限制 | 计算单元利用率~50%     |
| 代码生成   | 2K   | ~1 FLOPs/byte    | I/O限制   | 内存控制器繁忙         |
| 长文档摘要  | 32K  | ~0.01 FLOPs/byte | 严重I/O限制 | 95%时间在内存访问      |
| 训练（全量） | 4K   | ~100 FLOPs/byte  | 计算限制    | Tensor Core利用率高 |
只有**训练**的时候是**计算密集**型

### 1.8.3 FlashAttention 的三大核心技术
1. **分块计算（Tiling / Blocking）**
    - 将 Q,K,V 切分成小块（tiles），每块大小适配 GPU 的 SRAM 容量（如 A100 的 192KB）。
	- 例如：块大小 = 128 tokens → 每次只处理 128×128 的局部注意力矩阵。
	- **关键效果**：避免生成完整的 N×N 矩阵，中间结果始终在 SRAM 内完成计算，**不写回 HBM**。
2. 在线softmax, 避免存储A=softmax(QKT)
	- 标准 Softmax 需要整行数据才能归一化，但分块后只能看到部分分数。
	- FlashAttention 为每个 query 行维护两个统计量：
	    - mimi​ ：当前最大值（用于数值稳定）
	    - lili​ ：指数和（用于归一化）
	- 每处理一个新块，就动态更新 mimi​ 和 lili​ ，并重缩放已累积的输出。
	- **数学等价性**：最终结果与标准 Softmax **完全一致**，无近似误差。
3. kernel融合
	- 将 “QK^T → Softmax → PV” 整个流程融合为 **单个 CUDA kernel**。
	- 所有操作在 SRAM 内“一气呵成”，中间结果 **永不写入 HBM**。
	- 极大减少 HBM 访问次数（可减少 10 倍以上）

| 指标       | 标准 Attention     | FlashAttention    |
| -------- | ---------------- | ----------------- |
| 显存复杂度    | $O(N^2)$ （需存 A ） | O(N) （只存 Q,K,V,O） |
| HBM 读写量  | 高（多次读写 A ）       | 极低（仅读 Q,K,V，写 O）  |
| 速度（长序列）  | 慢（IO-bound）      | 快 2~4 倍（A100 上）   |
| 最大支持序列长度 | 受限于 $N^2$ 显存     | 可轻松处理 8K~64K      |

### 1.8.4 如何解决IO瓶颈
| 传统方法                | FlashAttention       |
| ------------------- | -------------------- |
| “先算完再存” → 大量 HBM 读写 | “边算边融合” → 最小化 HBM 访问 |
| 忽略内存层次结构            | 显式建模 SRAM ↔ HBM 数据流  |
| 计算和 IO 串行           | 计算和 IO 隐式重叠（通过分块）    |

它把 **算法设计** 和 **硬件特性（内存层次）** 结合起来，属于 **近似计算？**  
→ **不！它是 exact（数学等价）的**，只是更聪明地安排计算顺序。

### 1.8.5 例子
#### 1.8.5.1  设定参数
- 序列长度：**N = 5**
- hidden size（每个 token 的向量维度）：**d = 4**
- 单头注意力（简化）
- 数据类型：FP32（方便手算）
- 因果掩码：**不用**（先看标准 attention）

我们有：
- **Q, K, V ∈ ℝ⁵ˣ⁴**
为了简单，我们用**随机但简单的数字**：
```python
Q = [ [1, 0, 0, 0], # q₀
	 [0, 1, 0, 0], # q₁ 
	 [0, 0, 1, 0], # q₂ 
	 [0, 0, 0, 1], # q₃ 
	 [1, 1, 1, 1] # q₄ ] 
 K = [ [1, 0, 0, 0], # k₀ 
	   [0, 1, 0, 0], # k₁ 
	   [0, 0, 1, 0], # k₂ 
	   [0, 0, 0, 1], # k₃ 
	   [1, 1, 1, 1] # k₄ 
	   ] 
V = [ [1, 0, 0, 0], # v₀ 
     [0, 1, 0, 0], # v₁ 
     [0, 0, 1, 0], # v₂ 
     [0, 0, 0, 1], # v₃ 
     [1, 1, 1, 1] # v₄ 
     ]
```
缩放因子：$\sqrt{ d }=\sqrt{ 4 }$ = **2**


#### 1.8.5.2 传统 Attention 计算（显存高）
- 步骤 1：计算 A = QKᵀ / 2
	- A\[i]\[j] = (qᵢ · kⱼ) / 2
		因为 qᵢ 和 kⱼ 是单位向量或全1向量：
		- q₀·k₀ = 1 → A[0][0] = 0.5
		- q₀·k₁ = 0 → A[0][1] = 0
		- ...
		- q₄·kⱼ = 1（对所有 j）→ A[4][j] = 1/2 = 0.5
		所以 A 矩阵为：
		```python
		A = [ [0.5, 0, 0, 0, 0.5], 
			  [0, 0.5, 0, 0, 0.5], 
			  [0, 0, 0.5, 0, 0.5], 
			  [0, 0, 0, 0.5, 0.5], 
			  [0.5, 0.5, 0.5, 0.5, 2.0] # q₄·k₄ = 4 → 4/2 = 2.0 ]
		```
		这是一个 **5×5 = 25 个 float** 的矩阵 → **必须存到显存！**

- 步骤2： P = softmax(A) 按行
	- 以第 0 行为例：
	- logits: [0.5, 0, 0, 0, 0.5]
	- max = 0.5
	- exp: [1, e⁻⁰·⁵≈0.6065, 0.6065, 0.6065, 1]
	- sum ≈ 1 + 0.6065×3 + 1 ≈ 3.8195
	- P[0] ≈ [0.2618, 0.1591, 0.1591, 0.1591, 0.2618]
	→ 又一个 **5×5 矩阵 P 存到显存！**

- 步骤 3：O = P @ V
	- O[0] = Σⱼ P[0][j] * vⱼ  
		= 0.2618_v₀ + 0.1591_v₁ + ... + 0.2618*v₄  
		= [0.2618+0.2618, 0.1591+0.2618, 0.1591+0.2618, 0.1591+0.2618]  
		= [0.5236, 0.4209, 0.4209, 0.4209]

→ 最终 O 是 5×4 矩阵。
**总显存峰值**：A (25 floats) + P (25 floats) + Q,K,V,O (5×4×4 = 80 floats) ≈ **130 floats**

#### 1.8.5.3 FlashAttention 怎么算？（不存 A 和 P！）
我们只演示 **计算输出的第 0 行 O[0]**，其他行同理。
目标：计算
$$O_{[0]}=\frac{\sum_{j=0}^{4}\exp(a_{0j}-m_{0})v_{j}}{\sum_{j=0}^{4}\exp(a_{0j}-m_{0})}$$
其中，$a_{0j}=\frac{q_{0}.k_{j}}{2}，m_{o}=Max(a_{0j})$
从上面知道：
- a₀ = [0.5, 0, 0, 0, 0.5]
- m₀ = 0.5

所以：

- 分子 = exp(0)*v₀ + exp(-0.5)*v₁ + exp(-0.5)*v₂ + exp(-0.5)*v₃ + exp(0)*v₄
- 分母 = exp(0) + 3×exp(-0.5) + exp(0)

但 FlashAttention **不会一次性算所有 j**，而是**分块流式计算并累加**。

| 项目           | 传统 Attention   | FlashAttention |
| ------------ | -------------- | -------------- |
| 是否存储 A (5×5) | ✅ 是（25 floats） | ❌ 否            |
| 是否存储 P (5×5) | ✅ 是（25 floats） | ❌ 否            |
| 中间变量大小       | O(N²) = 25     | O(d) = 4（每行）   |
| HBM 写入次数     | 多次（写 A, P）     | 0（中间结果全在 SRAM） |
| 最终结果         | 相同             | 相同（exact）      |

## 2.1 微调方式

微调方法的选择核心在于：**你需要模型改变什么？** 是改变它的“说话方式（格式）”，还是改变它的“知识储备”，或者是“推理逻辑”。
- 说话方式（风格、格式）
- 知识储备 （垂直领域知识注入）
- 推理逻辑

        *   *Rank 设置*：需要较高的 Rank (r=64, 128 甚至 256)。低 Rank 即使拟合了训练数据，也往往是“死记硬背”，泛化性差。

### 2.1.2 场景二：格式规范与风格迁移 (Format/Style Transfer)
*   **任务举例**：让模型输出 JSON、SQL 语句、扮演特定角色（如“猫娘”）、摘要生成。
*   **特点**：模型本身懂得语言和逻辑，只是不知道你想要的输出格式。
*   **推荐策略**：
    *   **首选**：**LoRA (Standard)**。
    *   *关键点*：通常只需要微调 Attention 层的 `q_proj`, `v_proj` 即可，或者加上 `k_proj`。
    *   *Rank 设置*：低 Rank (r=8, 16) 足够。过高的 Rank 反而容易过拟合，导致模型只会输出 JSON 而丧失了通用的对话能力。
    *   **备选**：**P-Tuning v 2 / Prefix Tuning**。对于极少样本（Few-shot）的格式对齐，Prompt Tuning 类的软提示微调有时候效果出奇的好，且参数量极小。

### 2.1.3 场景三：逻辑推理能力增强 (Reasoning Enhancement)
*   **任务举例**：复杂的数学题（CoT）、代码逻辑修复、Agent 规划。
*   **特点**：这是最难的。单纯的 SFT（有监督微调）往往只能让模型学会“模仿推理的步骤”，而不是真正学会“推理”。
*   **推荐策略**：
    *   **SFT + DPO/PPO**。仅仅靠 SFT 很难提升逻辑上限。通常需要先用 SFT 甚至 LoRA 让他学会输出 CoT 的格式，然后必须接入 **RLHF (如 DPO - Direct Preference Optimization)**。
    *   **数据为王**：这里微调方式不重要，重要的是数据质量（必须包含详细的推理步骤）。

## 2.2 结合任务结构的 LoRA 插入位置与策略

LoRA (Low-Rank Adaptation) 的本质是在原有权重 $W$ 旁路增加 $\Delta W = B \times A$。

### 2.2.1 LoRA 插在 Attention 还是 FFN 更合适？
**结论**：**成年人全都要（Target All Linear Layers）是目前的 SOTA（最佳实践）。**

*   **Attention ($W_q, W_k, W_v, W_o$)**：
    *   **作用**：控制“注意力”分配，即模型该看哪里。
    *   **适合任务**：需要捕捉上下文依赖关系的任务（如摘要、长文本理解）。
    *   **早期观点**：最早的 LoRA 论文主要针对 `q_proj` 和 `v_proj`。这对于改变模型的“关注点”很有效，适合风格迁移。

*   **FFN (MLP / $W_{gate}, W_{up}, W_{down}$) - 关键所在**：
    *   **作用**：根据 Transformer 的机制研究（如 Meng et al., 2022 的 ROME 论文），FFN 层被认为是**存储事实性知识（Key-Value Memories）**的主要区域。
    *   **数据表现**：QLoRA 论文（Dettmers et al., 2023）实验表明，只微调 Attention 层的效果远不如同时微调 Attention + FFN。
    *   **案例**：在医学微调任务中，如果不微调 FFN，模型可能学会了医生的语气，但开出的药方全是通用的（比如“多喝热水”），只有微调 FFN，才能让其根据症状关联到具体的特异性药物。

### 2.2.2 动态 Rank 与 AdaLoRA
**问题**：所有的层都需要同样的 rank (比如 r=16) 吗？
**答案**：不需要。不同层对任务的贡献度不同。

*   **AdaLoRA (Adaptive LoRA)**：
    *   **原理**：它根据权重矩阵的奇异值（SVD）重要性，动态分配 rank。对于重要的层，给更高的 rank；不重要的层，给低 rank 甚至裁剪掉。
    *   **优势**：在参数总量不变的情况下，AdaLoRA 通常比标准 LoRA 效果更好。
    *   **策略建议**：如果你不知道哪一层重要，使用 AdaLoRA 或者类似的动态剪枝策略。通常来说，**靠近输出层的参数往往对特定任务更敏感**，而底层的参数更偏向通用的语法特征。

### 2.2.3 层级 LoRA (Layer-wise LoRA) 策略
*   **底层 (Lower Layers)**：负责词法、语法、浅层语义。
    *   *策略*：如果你只是做简单的文本分类或格式转换，可以冻结底层，只微调高层，节省显存。
*   **高层 (Upper Layers)**：负责抽象语义、逻辑推理、知识融合。
    *   *策略*：对于复杂的逻辑任务或知识注入，高层的 LoRA Rank 应该设置得更大，或者给予更大的学习率（Layer-wise Learning Rate Decay 的反向应用）。

## 2.3 多任务共享 + 任务专属 Adapter

在实际生产（如 SaaS 平台或综合 Agent）中，我们往往希望一个模型能干多件事。

### 2.3.1 架构设计：Shared Trunk + Branch Adapters

1.  **Shared LoRA (通用底座增强)**：
    *   在一个大规模的混合数据集（Instruction Tuning Data）上训练一个通用的 LoRA 模块。
    *   **目的**：让模型更听话，理解指令，作为一个增强版的 Base。

2.  **Task-Specific LoRA (任务专家)**：
    *   针对特定任务（如“写 SQL”、“翻译”、“医疗问答”）训练独立的小 LoRA。
    *   **Rank**：这些专属 LoRA 的 Rank 可以很小 (r=8)。

### 2.3.2 动态路由与混合 (LoRA-Hub / MoE-LoRA)
*   **线性加权**：推理时，权重 $W' = W_{base} + \alpha_1 \cdot LoRA_{shared} + \alpha_2 \cdot LoRA_{task}$。
    *   *风险*：直接相加可能会导致参数冲突（Interference），导致模型输出乱码。
*   **LoRA 作为路由专家 (MoE)**：
    *   使用一个小的 Router 网络（Classifier），根据用户输入的 Prompt，动态决定激活哪一个 LoRA Adapter。
    *   **案例**：用户问“帮我写个 Python 脚本”，Router 激活 `Coding_LoRA`；用户问“合同怎么写”，Router 激活 `Legal_LoRA`。这是目前企业级应用最稳健的架构。

## 2.4 ：微调失效的原因深度解析（避坑指南）

很多时候微调失败不是算法问题，是细节问题。

### 2.4.1 虚假的 Loss 下降 (Distribution Shift)
*   **现象**：Training Loss 一路狂跌，Validation Loss 也不错，但生成出来的东西就是不说人话，或者只会重复输入。
*   **原因**：
    *   **Prompt 格式错误**：训练时的 Prompt Template（如 `<|user|>...<|assistant|>`）和推理时即使有一个空格的差别，都会导致模型崩溃。这是最常见的原因。
    *   **EOS Token 缺失**：训练数据里没有加 `<EOS>`（结束符），导致模型学会了永远不停止说话，直到最大长度。

#### 2.4.1.1 灾难性遗忘 (Catastrophic Forgetting)
*   **现象**：微调完医疗模型后，问它“你好”，它回答“建议服用阿莫西林”。通用能力丧失。
*   **原因**：领域数据密度过高，改变了参数分布的重心。
*   **解法**：
    *   **数据混合 (Replay)**：在微调数据中，混入 10%-20% 的通用对话数据（如 Alpaca, ShareGPT）。这是**必须**做的。
    *   **减小 Rank**：限制模型改变的幅度。

### 2.4.2 过拟合与幻觉增强
*   **现象**：模型对训练集里的问题回答得完美，稍微改一个字就开始胡说八道。
*   **原因**：数据量太少（比如只有 100 条），但 Epoch 跑了太多（比如 10 个 Epoch），或者 Rank 太大（r=64）。
*   **经验法则**：对于 < 1000 条的数据，Epoch 不超过 3-4，Rank 建议 8 或 16，Dropout 设为 0.05 或 0.1。

### 2.4.3 评估错位
*   **现象**：用 BLEU/ROUGE 分数看微调效果很好，人工看很差。
*   **原因**：生成式任务不能只看 n-gram 重叠。
*   **解法**：使用 **LLM-as-a-Judge**。让 GPT-4 对微调后的模型输出进行打分，或者建立特定任务的测试集（Test Set）计算准确率（如代码通过率、选项正确率），而不是文本相似度。

### 2.4.4 总结建议

如果你现在要开始一个新任务：

1.  **策略**：先用 **QLoRA**，目标模块选 **All Linear** (Attn + FFN)。
2.  **配置**：Rank 起手 **32** 或 **64**，Alpha 设为 Rank 的 2 倍（即 64 或 128）。
3.  **数据**：准备高质量数据，务必混入 **通用数据** 防止变傻。
4.  **调试**：如果你发现模型学不会知识，加大 Rank 并确保 FFN 被训练；如果你发现模型变傻了，减小 Rank 或增加通用数据比例。

### 2.4.5 参数维度：Rank 的选择与本质

**核心论点**：大模型的改动具有“低本征维度（Low Intrinsic Dimension）”，即大部分参数其实不需要动，动一点点关键的投影就能改变输出。

#### 2.4.5.1 证据 C：LoRA 原始论文
*   **论文来源**：*Hu et al., ICLR 2022*
*   **实验设计**：在 GPT-3 175 B 上进行 WikiSQL 和 MultiNLI 任务微调，测试不同 Rank (r) 的效果。
*   **数据表现 (WikiSQL Accuracy)**：
    *   `r=1`: 73.4%
    *   `r=2`: 73.6%
    *   `r=4`: 73.8%
    *   `r=8`: 73.8%
    *   `r=64`: 73.5%
*   **反直觉现象**：你可以看到，从 r=4 增加到 r=64，**效果并没有提升，甚至略有下降**。
*   **原文洞察**：
    > "A low rank is sufficient... The update matrix $\Delta W$ has a very low intrinsic rank."
    > (一个低秩就足够了……更新矩阵 $\Delta W$ 具有非常低的本征秩。)
*   **子空间相似性实验**：作者对比了 r=8 和 r=64 训练出来的两个矩阵，发现它们共享了很大一部分“子空间”。这意味着 r=64 学到的多余维度主要是噪声。
*   **结论应用**：
    *   对于**格式对齐/简单任务**：r=8 足够，甚至是杀鸡用牛刀。
    *   **反转**：但在后来的**复杂逻辑/代码任务**（如 Magicoder, DeepSeek-Coder 微调）中，社区发现 **r=64 或 r=128** 更好。这是因为“逻辑重组”比“格式对齐”需要更高的本征维度，原始 LoRA 论文的任务相对简单（分类和简单生成）。

---

### 2.4.6 数据维度：LIMA 假设 (Less Is More for Alignment)

**核心论点**：SFT（有监督微调）的主要作用不是学习新知识，而是**激活**模型预训练时已经学会的知识和格式。

#### 2.4.6.1 证据 D：LIMA 论文
*   **论文来源**：*Zhou et al. (Meta AI), NeurIPS 2023*
*   **实验设计**：
    *   模型 A：在 50,000 条常规指令数据上微调。
    *   模型 B (LIMA)：仅在 **1,000 条** 人工精选的高质量数据上微调。
*   **数据表现**：
    *   在人类评估（Human Eval）中，LIMA 模型生成的回复质量，**击败了** 基于 50 k 数据训练的 Alpaca，甚至在 43% 的情况下优于 GPT-4。
*   **原文洞察**：
    > "Superficial Alignment Hypothesis: A model’s knowledge and capabilities are learnt almost entirely during pretraining, while alignment teaches it which sub-distribution of formats should be used."
    > (表面对齐假设：模型的知识和能力几乎完全是在预训练阶段学到的，而对齐（微调）只是教它应该使用哪种格式的子分布。)
*   **结论应用**：
    *   如果你做微调，**清洗数据的时间应该占 80%**。
    *   如果你有 10 万条从网上爬下来的脏数据，不如人工清洗出 1000 条黄金数据。
    *   这也解释了为什么微调容易发生“灾难性遗忘”——你用 1000 条特定分布的数据去强行拉扯模型，它很容易忘记原本广博的“预训练分布”。

### 2.4.7 优化维度：LoRA+ (为什么 A 和 B 不能一视同仁)

**核心论点**：在标准 LoRA 中，矩阵 A（降维）和矩阵 B（升维）的学习效率是不一样的。

#### 2.4.7.1 证据 E：LoRA+ 论文
*   **论文来源**：*Hayou et al., 2024*
*   **理论分析**：LoRA 的更新量是 $\Delta W = B A$。作者从数学上证明了，为了让训练最快收敛，矩阵 B 的学习率应该远大于矩阵 A 的学习率。
*   **原文洞察**：
    > "Standard LoRA training is suboptimal... Matrix B should have a higher learning rate to match the initialization scale."
    > (标准 LoRA 训练不是最优的……矩阵 B 应该拥有更高的学习率以匹配初始化尺度。)
*   **工程建议**：
    *   这就是为什么现在的微调框架（如 LLaMA-Factory）中会有 `lora_alpha` 这个参数。
    *   通常设置 `alpha = 2 * rank` (比如 r=16, alpha=32)。这本质上是在放大更新的权重，模拟了让 B 矩阵学得更“猛”一点的效果。
    *   **LoRA+** 更是直接建议：为 A 和 B 设置不同的 Learning Rate (ratio $\lambda \approx 10^2$)。

## 2.5 为什么要微调 FFN？知识到底在哪？
^7fe2c7

**核心论点**：Transformer 的 Attention 负责“**路由信息**（关注哪里）”，而 FFN（前馈网络）负责“存储知识（是什么）”。

### 2.5.1 证据 A：ROME 论文 (Locating and Editing Factual Associations in GPT)
*   **论文来源**：*Meng et al., NeurIPS 2022*
*   **实验设计**：研究人员试图找出 GPT-2 在回答“埃菲尔铁塔在哪？”（答案：巴黎）时，大脑里哪块区域亮了。他们使用了**因果追踪（Causal Tracing）技术**，通过干扰并恢复特定层的激活状态，看输出概率的恢复情况。
*   **数据表现**：
    *   实验发现，当恢复 **中层前馈网络 (MLP/FFN)** 的激活时，模型恢复正确答案的概率最高。
    *   Attention 层的恢复对事实性知识的影响较小。
*   **原文洞察**：
    > "Fact retrieval from the MLP weights can be modeled as a key-value memory lookup."
    > (从 MLP 权重中检索事实可以被建模为一个键值记忆查找过程。)
*   **结论应用**：如果你做**行业知识注入**（如医疗、法律），必须微调 FFN。如果你只微调 Attention，模型学会了“医生的语气”，但要把“头疼”关联到“阿司匹林”这一步（Key-Value 映射），是在 FFN 里完成的。

### 2.5.2 证据 B：QLoRA 论文
*   **论文来源**：*Dettmers et al., NeurIPS 2023*
*   **实验设计**：对比仅微调 Attention 层 vs. 微调所有线性层（Attention + FFN）。
*   **数据表现 (MMLU 5-shot Accuracy)**：
    *   `LoRA (Attention only)`: 精度 **47.1%**
    *   `LoRA (All Linear Layers)`: 精度 **48.3%**
    *   注：在 Vicuna 基准测试中，All Linear 的表现接近 GPT-4 的 99.3%，而仅微调 Attention 只有 97. X%。
*   **结论应用**：Target All Linear Layers 是目前的标准动作，虽然参数量增加了，但性能提升是实打实的。

## 2.6 为什么垂直领域知识的注入需要全参微调

^4dc381

要回答“为什么垂直领域知识注入需要全量微调（Full Fine-tuning）”，我们需要打破“微调”这个笼统的概念，从**信息论**和**模型参数空间**的角度来理解。

一言以蔽之：**LoRA 的本质是“对齐（Alignment）”，而全量微调（或增量预训练）的本质才是“学习（Acquisition）”。**

以下是四个层面的深度解析：

### 2.6.1 数学层面：本征维数（Intrinsic Dimension）的差异

我们在之前的 LoRA 论文（Hu et al., 2022）中提到过“低本征维数假设”。这个假设成立的前提是：**模型已经学会了知识，只是不知道该怎么表达。**

- **格式/风格调整**：这是一个**低秩（Low Rank）**的变化。
    
    - 比如，模型已经知道 1+1=2，你让它用 JSON 输出 `{"result": 2}`。这不需要改变太多神经元的连接，只需要调整几个关键的路由权重即可。
    - $\Delta W$ 的秩很低，LoRA (r=8) 就能覆盖。
        
- **新知识注入**：这是一个**满秩（Full Rank）或高秩**的变化。
    
    - 比如，模型只知道“苹果是水果”，你需要教会它“苹果（Apple）是一家位于库比蒂诺的科技公司，CEO 是库克”。
    - 这意味着模型内部的词嵌入（Embedding）关系、前馈网络（FFN）中的 Key-Value 映射都需要进行大规模重组。
    - **数学矛盾**：试图用两个小矩阵 $B \times A$ （秩为 r）去拟合一个蕴含着大量新信息的复杂变化矩阵 $\Delta W_{knowledge}$ ​，会产生巨大的**信息压缩损失**。就像试图用一张便利贴抄写整本百科全书，写不下的。
        

### 2.6.2 物理存储层面：参数容量与压缩率

大模型其实是一个巨大的**有损压缩数据库**。
- **全量微调 (FFT)**：
    - 你拥有 7 B 或 70 B 个参数的读写权限。
    - 海量的 FFN 层（占模型参数的 2/3）是存储事实性知识的“硬盘”。全量微调允许你改写这块硬盘上的任何数据，建立新的突触连接来存储新的概念。
        
- **LoRA**：
    - 通常 LoRA 的可训练参数量只有原模型的 **0.1% ~ 1%**。
    - **信息熵限制**：根据香农信息论，1% 的参数量所能承载的比特数（Bit）是有限的。如果你灌入的垂直领域数据（如千万级的医疗文献）所包含的信息量超过了这 1% 参数的承载上限，模型就根本“记不住”。
    - 结果就是：模型可能学会了医疗文献的**文风**（开头写“患者诉...”），但对于具体的病理机制和药物配伍，它依然在用通用的（错误的）概率进行猜测。
        

### 2.6.3 训练机制层面：增量预训练 (Continual Pre-training) vs SFT

在工业界（如金融大模型、法律大模型），“注入知识”通常不叫“微调”，而叫**增量预训练（Continual Pre-training, CPT）**。
- **流程**：
    1. **CPT (Full Fine-tuning)**: 使用海量的无监督领域文档（PDFs, Papers），对全量参数进行训练。
        - _目的_：改变模型的底层分布，让它理解“借贷”在金融语境下和日常语境下的区别。
            
    2. **SFT (LoRA)**: 使用少量的问答对（Q&A）。
        - _目的_：教会模型怎么用刚才学到的知识来回答用户问题。
            
- **如果不做第一步会怎样？**
    - 如果直接跳过 CPT，只用 LoRA 跑 SFT，模型会出现严重的**幻觉（Hallucination）**。因为它被迫用通用的逻辑去强行解释它没见过的专业术语，就像一个文科生试图用修辞手法去解释量子力学。
        

### 2.6.4 神经科学类比：短期记忆 vs 长期记忆

- **Context Window (RAG / Prompt)**：好比**海马体（短期工作记忆）**。你把知识写在 Prompt 里，模型看着能回答，但没真正学会，关掉窗口就忘了。
- **LoRA**：好比**小脑（运动/技能记忆）**。你学会了骑车、学会了写八股文、学会了用 SQL 格式说话。这是技能层面的适应。    
- **全量微调**：好比**大脑皮层（长时语义记忆）**。你需要真正改变神经元的突触强度，把知识刻在大脑沟回里。
    

---

### 2.6.5 关键判据：什么时候**必须**全量微调？

并不是所有垂直领域都需要全量微调，请参考以下判据：
1. **新术语密度**：
    - 如果你的领域包含大量预训练模型**没见过的词汇**（如公司内部特定的项目代码、新型药物的化学式），LoRA 基本无效。因为 Tokenizer 甚至可能把这些词切碎成无意义的片段，只有全量微调（甚至需要扩充词表 Embedding）才能解决。
        
2. **逻辑重构**：
    - 如果你的领域逻辑与通用逻辑**相悖**。
    - _例子_：在通用世界里，红色代表危险/停止；但在某些特殊的工业控制系统中，红色代表“运行正常”。这种颠覆底层认知的改变，LoRA 很难扭转（Weight strong enough to override base weights），通常需要全量微调。
        
3. **语言切换**：
    - 比如 Llama 2 原生中文能力很差。如果你想做一个纯中文强的模型，仅靠 LoRA 很难弥补中英文在语法结构和语义空间上的巨大鸿沟，通常需要全量增量预训练（如 Yi, Qwen 的做法）。
        

### 2.6.6 避坑建议：RAG 才是正解？

最后需要特别提醒的是，**大部分企业想做的“知识注入”，其实都不应该用微调（无论是 LoRA 还是全量）。**
- **事实性知识（Fact）**更新极快（如今天的股价、最新的法律条文）。
- 微调（即使是全量）也是有滞后性的，且容易产生幻觉。
    
- **最佳实践**：
    - **知识**交给 **RAG (检索增强生成)**：外挂知识库，准确、可溯源、易更新。
    - **微调**交给 **LoRA**：微调模型让它学会“如何阅读 RAG 检索回来的文档”以及“如何以专业的口吻回答”。
-
