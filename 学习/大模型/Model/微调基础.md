# 1.  Llama-factory (提供图形化界面)
## 1.1 lora
- 秩
	- 推荐秩
		- 32
	- 缩放系数
		- 64（秩的 2 倍）
- Qlora
	- 节省显存（把显存给到批次大小和秩上，提升效果）
	- 量化等级
		- 4
## 1.2 评估标准
- 生成式模型评估主流方法
	- 主观评估
		- 通过核心问题对模型提问，人为评估（**主流**）
	- 客观评估（非主流）
		- 通过一些具体的评估指标来判定模型**输出的内容**与**标准答案**之间的**相似度**
		- <font color="#ff0000">文本命中率</font>
- 验证集评估
	- 不是很关注验证数据的效果，验证集的 loss 一般呈现上升-->平缓-->下降
	- 法律、医疗行业，这种<font color="#ff0000">用词规范</font>的行业，需要要求验证集的效果（答复和标签之间的相似度足够高）
	- 其他行业，可能需要模型有一方面的自我发挥（验证集的 loss）不需要特别要求
- **如果验证集和训练集的表达方式（数据分布、格式、语言风格、任务表述等）不一致，验证集的 loss 很可能降不下来**，即使训练集 loss 正常下降，模型在验证集上表现也会很差。这种现象通常不是模型“学不好”，而是**验证集和训练集之间存在“分布偏移”或“语义鸿沟”**

## 1.3 量化
- 微调量化
	- Qlora，参数量化后，仍然在进行**动态训练**，因此对于模型精度的影响很小
	- 量化的精度损失，可以通过模型训练弥补回来
	- Qlora 节省显存，可以适当提升批次样本数量，批次样本越大越好，精度降低的影响很小
	- 只在训练过程中进行量化，训练完成后进行反量化操作，所以模型的<font color="#ff0000">导出数据类型是不变</font>的
- 导出量化（<font color="#ff0000">不推荐</font>）
	- 已经训练完成，并测试通过，要对模型导出部署时
	- 最早出现在小模型的工业化落地，任务场景单一，即使牺牲精度也可以保证效果
	- 一般来讲，导出量化是<font color="#ff0000">牺牲</font>模型的<font color="#ff0000">精度</font>来**提升模型的推理速度**
	- 场景
		- 对模型的精度要求不高，且需要压缩硬件成本

Ollama 社区上的模型基本都是经过导出量化，所以都是个人用户在用

# 2 不同框架微调、部署差异解决
- 原因
	- Llama-factory 框架的<font color="#c00000">对话模板</font>与**大模型自带的对话模板**是不同的

## 2.1 对话模板
`Tokenizer_config.josn `文件内存在 chat_template 
- 定义角色（系统、用户）
- 定义了生成模型**以何种方式**进行回复
- 不同框架、模型的对话模板**不一致**,各个框架为了高度集成各个模型（集成各个模型的数据处理方式），它定义了一些通用模型的对话模板

## 2.2 解决方法
- vllm 支持使用自定义模板[[学习/大模型/Model/文件资料/【资料】vllm与LMDeploy如何自定义对话模板.pdf]]
- 为了使语言模型支持聊天协议，vLLM 要求模型在其 tokenizer 配置中包含聊天模板。聊天模板是一个 Jinja2 模板，用于指定角色、消息和其他特定于聊天的 token 如何在输入中编码.
	```shell
	vllm serve <model> --chat-template ./path-to-chat-template.jinja
	```

这里的`jinja`文件需要自己生成，生成方式如下：
```python
# mytest.py
import sys
import os

# 将项目根目录添加到 Python 路径
root_dir = os.path.dirname(os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__)))))
sys.path.append(root_dir)

from llamafactory.data.template import TEMPLATES
from transformers import AutoTokenizer

# 1. 初始化分词器（任意支持的分词器均可）
tokenizer = AutoTokenizer.from_pretrained("/root/autodl-tmp/llm/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B")

# 2. 获取模板对象
template_name = "qwen"  # 替换为你需要查看的模板名称
template = TEMPLATES[template_name]

# 3. 修复分词器的 Jinja 模板
template.fix_jinja_template(tokenizer)

# 4. 直接输出模板的 Jinja 格式
print("=" * 40)
print(f"Template [{template_name}] 的 Jinja 格式:")
print("=" * 40)
print(tokenizer.chat_template)
```

# 3 分布式微调
## 3.1 基本概念
- **分布式训练**
	- 单机多卡
	- 多机多卡
- **原因**
	- 模型太大（千亿），卡的性能不够
	- 加速训练过程
- **核心方式**
	- **数据并行**（Data Parallelism）
		-  原理
		  在**各个GPU上**都拷贝一份**完整模型**，各自吃一份数据，算一份梯度，最后对**梯度进行累加**来更新整体模型。将数据划分为**多个批次**，分发到**不同设备**，每个设备拥有**完整的模型副本**。
		- 挑战
		  **通信开销大**，显存占用高（需存储完整模型参数和优化器状态）
		- 同步方式
		  通过 All-Reduce 操作同步梯度（如 PyTorch 的 DistributedDataParallel）
	- **模型并行**（Model Parallelism）
		- 原理：将模型切分到不同设备（如按层或张量分片）。
		- 类型
		  横向并行（层拆分）：将模型的层分配到不同设备。
		  纵向并行（张量拆分）：如 Megatron-LM 将矩阵乘法分片。
		- 挑战：**设备间通信频繁**，负载均衡需精细设计。
	- **流水线并行**（Pipeline Parallelism）
		- 原理：将模型**按层**划分为多个阶段（stage），**数据分块**后按流水线执行。
		- 优化：**微批次**（Micro-batching）减少**流水线气泡**（Bubble）。
		- 挑战：需平衡阶段划分，避免资源闲置。
	- **混合并行**（3 D 并行）
		- 组合策略：结合数据并行、模型并行、流水线并行，典型应用如训练千亿级模型。
		- 案例：微软 Turing-NLG、Meta 的 LLaMA-2。
## 3.2 数据并行(DP)
数据并行的<span style="background:#ff4d4f">核心思想</span>是：**在各个GPU上都拷贝一份完整模型，各自吃一份数据，算一份梯度，最后对梯度进行累加来更新整体模型**。理念不复杂，但到了大模型场景，**巨大的存储和GPU间的通讯量**就是系统设计要考虑的重点了。
### 3.2.1 DP 数据并行
**DP（Data Parallelism）**：最早的数据并行模式，一般采用参数服务器这一编程框架，实际中多用于**单机多卡**
- 架构
  ![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928151038302.png)
- 计算过程
    - 若干块**计算GPU**，如图中GPU0~GPU2；1块**梯度收集GPU**，如图中AllReduce操作所在GPU。
    - 在每块计算GPU上都拷贝一份完整的模型参数。
    - 把一份数据X（例如一个batch）均匀分给不同的计算GPU。
    - 每块计算GPU做一轮FWD和BWD后，算得一份梯度G。
    - 每块计算GPU将自己的梯度**push**给梯度收集GPU，做聚合操作。这里的聚合操作一般指**梯度累加**。当然也支持用户自定义。
    - 梯度收集GPU聚合完毕后，计算GPU从它那**pull**下完整的梯度结果，用于更新模型参数W。更新完毕后，计算GPU上的模型参数依然保持一致。
    - **聚合再下发梯度的操作，称为AllReduce**。

实现DP的一种经典编程框架叫<span style="background:#ff4d4f">参数服务器</span>，在这个框架里，**计算GPU称为Worker**，**梯度聚合GPU称为Server**。在实际应用中，为了尽量**减少通讯量**，一般可选择一个Worker同时作为Server。比如可把梯度全发到GPU0上做聚合
![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928151427884.png)
- 缺点
  - **存储开销大**。每块GPU上都存了一份完整的模型，造成冗余。关于这一点的优化，我们将在后文ZeRO部分做讲解。
  - **通讯开销大**。Server需要和每一个Worker进行梯度传输。当Server和Worker不在一台机器上时，Server的带宽将会成为整个系统的计算效率瓶颈。
- 改进
  当Server在搬运数据，计算梯度的时候，Worker们在干嘛呢？当然是在**聚众摸鱼**，于是**梯度异步更新**这一管理层略诞生了。

- 梯度异步更新
  ![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928152107317.png)
  上图刻画了在**梯度异步更新**的场景下，某个Worker的计算顺序为：
- 在第10轮计算中，该Worker正常计算梯度，并向Server发送push&pull梯度请求。
- 但是，该Worker并不会实际等到把聚合梯度拿回来，更新完参数W后再做计算。而是直接拿旧的W，吃新的数据，继续第11轮的计算。**这样就保证在通讯的时间里，Worker也在马不停蹄做计算，提升计算通讯比。**
- 当然，异步也不能太过份。只计算梯度，不更新权重，那模型就无法收敛。图中刻画的是**延迟为1**的异步更新，也就是在开始第12轮对的计算时，必须保证W已经用第10、11轮的梯度做完2次更新了。

总结一下，**异步很香，但对一个Worker来说，只是等于W不变，batch的数量增加了而已，在SGD下，会减慢模型的整体收敛速度**。异步的整体思想是，比起让Worker闲着，倒不如让它多吃点数据，虽然反馈延迟了，但只要它在干活在学习就行。

### 3.2.2 分布式数据并行(DDP)
受通讯负载不均的影响，**DP一般用于单机多卡场景**。
因此，DDP作为一种更通用的解决方案出现了，既能多机，也能单机。**DDP首先要解决的就是通讯问题：将Server上的通讯压力均衡转到各个Worker上。实现这一点后，可以进一步去Server，留Worker。**
前文我们说过，聚合梯度 + 下发梯度这一轮操作，称为AllReduce。**接下来我们介绍目前最通用的AllReduce方法：Ring-AllReduce**。它由百度最先提出，非常有效地解决了数据并行中通讯负载不均的问题，使得DDP得以实现。
#### 3.2.2.1 Ring-AllReduce
如下图，假设有4块GPU，每块GPU上的**梯度数据**也对应被切成4份。AllReduce的最终目标，就是让每块GPU上的数据都变成箭头右边汇总的样子。
![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928152918686.png)
Ring-ALLReduce则分两大步骤实现该目标：**Reduce-Scatter**和**All-Gather。**
- **Reduce-Scatter**  
  定义网络拓扑关系，使得每个GPU只和其相邻的两块GPU通讯。每次发送对应位置的数据进行**累加**。每一次累加更新都形成一个拓扑环，因此被称为Ring。
  ![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928153143950.png)
![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928153158380.png)
一次累加完毕后，蓝色位置的数据块被更新，被更新的数据块将成为下一次更新的起点，继续做累加操作。
![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928153705345.png)
![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928153716845.png)
**3次**更新之后，每块GPU上都有一块数据拥有了对应位置完整的聚合（图中红色）。此时，Reduce-Scatter阶段结束。进入All-Gather阶段。目标是把红色块的数据广播到其余GPU对应的位置上。

- All-Gather
	如名字里Gather所述的一样，这操作里依然按**相邻GPU对应位置进行通讯**的原则，但对应位置数据不再做相加，而是**直接替换**。All-Gather以红色块作为起点。
	![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928153949794.png)
	![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928153958407.png)

#### 3.3.2.2 Ring-AllReduce通讯量分析

假设模型参数W的大小为 $\phi$，GPU个数为 $N$。则梯度大小也为 $\phi$，每个梯度块的大小为 ${\phi}\over{N}$   
对单卡GPU来说（只算其send通讯量）：

- Reduce-Scatter阶段，通讯量为 $({N-1}){{\phi}\over{N}}$ 
- All-Gather阶段，通讯量为 $({N-1}){{\phi}\over{N}}$ 

**单卡总通讯量为**$2({N-1}){{\phi}\over{N}}$ 
随着N的增大，可以近似为 **$2\phi$** 。**全卡总通讯量为 $2N\phi$**
  
而对前文的DP来说，它的Server承载的通讯量是 $N\phi$，Workers为 $N\phi$，全卡总通讯量依然为 $2N\phi$。
**虽然通讯量相同，但搬运相同数据量的时间却不一定相同**。DDP把通讯量均衡负载到了每一时刻的每个Worker上，而DP仅让Server做勤劳的搬运工。当越来越多的GPU分布在距离较远的机器上时，DP的通讯时间是会增加的。
![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250928155802985.png)
在多Server的模式下，进一步，每个Server可以只负责维护和更新某一块梯度（也可以某块梯度+参数一起维护），此时虽然每个Server仍然需要和所有Worker通讯，但它的带宽压力会小非常多。经过调整设计后，依然可以用来做DDP。虽然这篇文章是用递进式的方式来介绍两者，但不代表两者间一定要决出优劣。
**Ring-AllReduce的方法，因为在之后的ZeRO，Megatron-LM中，它将频繁地出现，是分布式训练系统中重要的算子。**



### 3.2.3 总结
1、在DP中，每个GPU上都拷贝一份完整的模型，每个GPU上处理batch的一部分数据，所有GPU算出来的梯度进行累加后，再传回各GPU用于更新参数  
2、DP多采用参数服务器这一编程框架，一般由若个计算Worker和1个梯度聚合Server组成。Server与每个Worker通讯，Worker间并不通讯。因此Server承担了系统所有的通讯压力。基于此DP常用于单机多卡场景。  
3、异步梯度更新是提升计算通讯比的一种方法，延迟更新的步数大小决定了模型的收敛速度。  
4、Ring-AllReduce通过定义网络环拓扑的方式，将通讯压力均衡地分到每个GPU上，使得跨机器的数据并行（DDP）得以高效实现。  
5、DP和DDP的总通讯量相同，但因负载不均的原因，DP需要耗费更多的时间搬运数据
  


## 3.3 deepSpeed 框架 (分布式训练框架)
- 定位：**微软**开源的分布式训练优化框架，支持千亿参数模型训练。
- 核心目标：降低大模型训练成本，提升显存和计算效率。
- 集成生态：与 PyTorch 无缝兼容，支持 Hugging Face Transformers 库。
### 3.3.1 <span style="background:#ff4d4f">核心技术</span>
- ZeRO（Zero Redundancy Optimizer）—— Adam 的改良
	- 原理：通过分片优化器状态、梯度、参数，消除数据并行中的<font color="#c00000">显存冗余</font>。
	- <span style="background:#40a9ff">阶段划分</span>：
		- ZeRO-1：**优化器状态**分片
		- ZeRO-2：**梯度分片** + 优化器状态分片 ——<font color="#00b050">单卡可运行</font>，但是希望<font color="#00b050">多卡加速</font>，模型未拆分，**训练最快**
		- ZeRO-3：**参数分片** + 梯度分片 + 优化器状态分片——<font color="#00b050">解决单卡训练显存不够</font>，模型拆分
	- 优势：**显存占用随设备数线性下降，支持训练更大模型**。
- 显存优化技术
	- 梯度检查点（Activation Checkpointing）：用时间换空间，**减少激活值显存**占用。
	- CPU Offloading：将优化器状态和梯度卸载到 CPU 内存。
	- 混合精度训练：FP 16/BP 16 与动态损失缩放（Loss Scaling）。
- 其他特性
	- 大规模推理支持：模型并行推理（如 ZeRO-Inference）。
	- 自适应通信优化：自动选择最佳通信策略（如 All-Reduce vs. All-Gather）。
### 3.2.2 优势与特点
- 显存效率高：ZeRO-3 可将显存占用<span style="background:#ff4d4f">降低至 1/设备数</span>。
- 易用性强：通过少量代码修改即可应用（如 DeepSpeed 配置 JSON 文件）。
- 扩展性优秀：支持千卡级集群训练。
- 开源社区支持：持续更新，与 Hugging Face 等生态深度集成。

### 3.2.3 使用场景
- 训练百亿/千亿参数模型（如 GPT-3、Turing-NLG）。
- 资源受限环境：单机多卡训练时通过 Offloading 扩展模型规模。
- 快速实验：通过 <span style="background:#affad1">ZeRO-2</span> **加速**中等规模模型训练。

### 3.3.4 模型转换
模型训练后会自动保存成 PTH 模型（例如 iter_2000. Pth ，如果使用了 DeepSpeed，则将会是一个文件夹）
我们需要利用 xtuner convert pth_to_hf 将其转换为 HuggingFace 模型，以便于后续使用
```shell
xtuner convert pth_to_hf ${FINETUNE_CFG} ${PTH_PATH} ${SAVE_PATH} 
# 例如：xtuner convert pth_to_hf internlm2_chat_7b_qlora_custom_sft_e1_copy.py ./iter_2000.pth ./iter_2000_
```

### 3.3.5 模型合并
如果使用了<span style="background:#ff4d4f"> LoRA / QLoRA </span>微调，则模型转换后将得到 <span style="background:#40a9ff">adapter 参数</span>，而并不包含原 LLM 参数
如果期望获得合并后的模型权重（例如用于后续评测），那么可以利用 xtuner convert merge
```shell
xtuner convert merge ${LLM} ${LLM_ADAPTER} ${SAVE_PATH}
# ${LLM}是 baseModel的地址
# ${LLM_ADAPTER} 是转换后的hf模型
# ${SAVE_PATH} 是存储地址
```

- 方法

## 5.1 剪枝
剪枝方法的结构性或者非结构性剪枝，**本质上只是对于模型参数进行mask**（通过矩阵的方式），并不能改变模型的大小，所以它的优势在于：**提升推理性能，但是不能改变模型的大小**

## 5.2 量化
- [ ] 待学习
量化一般指Int8, 但是当前大模型主要用的是Int4
小模型量化不参与训练，但是目前<font color="#2DC26B">大模型是参与训练的</font>。
通过量化+反量化的方式，提升计算速度（计算时使用Int8，权重保存也是Int8），计算完成反量化为FP32
既可以**降低模型的体积又可以提升运算速度**，并且在训练过程中产生，<span style="background:#ff4d4f">结果是可控的，量化后精度损失可以控制在0.1%左右</span>
降低对设备性能的依赖

> [!attention] 实际使用
> 
> 其实主要还是要从设备（硬件）上去提升性能，量化的操作尽量少，他还是会牺牲性能，大模型其实更应该关注模型效果

## 5.3 知识蒸馏
原理：**把大模型的“知识”迁移到小模型中**，让小模型在保持较小体积和较低推理成本的同时，尽可能复现大模型的性能

![image.png](https://learning-1316972768.cos.ap-nanjing.myqcloud.com/%E5%AD%A6%E4%B9%A0/largeModel/20250925204144930.png)
你可以把大模型想象成一位“博学的老师”，小模型是一个“小学生”。  
老师通过“答题”的方式，把自己的“解题思路”传授给学生，而不是直接告诉学生标准答案。

1. 教师模型训练（Teacher Training）
	- 先训练好一个性能强的大模型（教师），它具备高准确率、强泛化能力。
	- 教师模型可以是如 GPT、DeepSeek、Llama 等大型语言模型。
    
2. 数据准备（Distillation Data）
	- 用教师模型对大量输入数据进行推理，生成“软标签”（soft labels）或“推理链”（如思维链 CoT）。
	- 软标签是模型输出的概率分布（如“猫：0.7，狗：0.2，车：0.1”），比硬标签（如“猫”）信息更丰富。

3. 学生模型训练（Student Training）
	- 学生模型（小模型）在相同输入下，输出自己的预测。
	- 训练目标是：**让学生模型的输出尽可能接近教师模型的输出**。

- 损失函数通常包括：
    - **原始损失**（如交叉熵）：保证学生也能拟合真实标签。
    - **蒸馏损失**（如 KL 散度）：衡量学生输出与教师软标签的差异。
    - 最终损失 = α * CE + (1-α) * KL

| 方法        | 简介             | 优点         | 缺点             |
| --------- | -------------- | ---------- | -------------- |
| **软标签蒸馏** | 学生模仿教师输出的概率分布  | 信息丰富，效果好   | 需访问教师模型输出，计算量大 |
| **硬标签蒸馏** | 学生模仿教师的最终预测结果  | 简单高效，资源占用低 | 信息损失大          |
| **协同蒸馏**  | 教师和学生一起训练，互相促进 | 可端到端优化     | 实现复杂，训练不稳定     |

| 要素                            | 描述                                                |
| ----------------------------- | ------------------------------------------------- |
| **教师模型（Teacher）**             | 大参数量模型，通常性能强、泛化好。                                 |
| **学生模型（Student）**             | 小参数量模型，目标是学习教师模型的行为。                              |
| **软标签（Soft Targets）**         | 使用教师模型输出的概率分布（logits 或 softmax），而不仅仅是 hard label。 |
| **温度缩放（Temperature Scaling）** | 用于平滑概率分布，使学生模型学到更多“暗知识”。                          |
| **损失函数设计**                    | 通常结合 hard loss（与真实标签）和 soft loss（与教师输出）。          |


- 案例
	- 教师模型：DeepSeek-R1（大模型）
	- 学生模型：Qwen 或 Llama 3.1（小模型）
	- 方法：教师生成 60 万条“推理链”数据，学生通过监督微调（SFT）模仿这些推理过程，从而学会“像老师一样思考”

<span style="background:#ff4d4f">知识蒸馏 = 让小模型“看懂”大模型的“思考方式”，而不是死记硬背答案</span>
