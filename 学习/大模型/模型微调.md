
# 1.  Llama-factory (提供图形化界面)
## 1.1 lora
- 秩
	- 推荐秩
		- 32
	- 缩放系数
		- 64（秩的 2 倍）
- Qlora
	- 节省显存（把显存给到批次大小和秩上，提升效果）
	- 量化等级
		- 4
## 1.2 评估标准
- 生成式模型评估主流方法
	- 主观评估
		- 通过核心问题对模型提问，人为评估（**主流**）
	- 客观评估（非主流）
		- 通过一些具体的评估指标来判定模型**输出的内容**与**标准答案**之间的**相似度**
		- <font color="#ff0000">文本命中率</font>
- 验证集评估
	- 不是很关注验证数据的效果，验证集的 loss 一般呈现上升-->平缓-->下降
	- 法律、医疗行业，这种<font color="#ff0000">用词规范</font>的行业，需要要求验证集的效果（答复和标签之间的相似度足够高）
	- 其他行业，可能需要模型有一方面的自我发挥（验证集的 loss）不需要特别要求
- **如果验证集和训练集的表达方式（数据分布、格式、语言风格、任务表述等）不一致，验证集的 loss 很可能降不下来**，即使训练集 loss 正常下降，模型在验证集上表现也会很差。这种现象通常不是模型“学不好”，而是**验证集和训练集之间存在“分布偏移”或“语义鸿沟”**

## 1.3 量化
- 微调量化
	- Qlora，参数量化后，仍然在进行**动态训练**，因此对于模型精度的影响很小
	- 量化的精度损失，可以通过模型训练弥补回来
	- Qlora 节省显存，可以适当提升批次样本数量，批次样本越大越好，精度降低的影响很小
	- 只在训练过程中进行量化，训练完成后进行反量化操作，所以模型的<font color="#ff0000">导出数据类型是不变</font>的
- 导出量化（<font color="#ff0000">不推荐</font>）
	- 已经训练完成，并测试通过，要对模型导出部署时
	- 最早出现在小模型的工业化落地，任务场景单一，即使牺牲精度也可以保证效果
	- 一般来讲，导出量化是<font color="#ff0000">牺牲</font>模型的<font color="#ff0000">精度</font>来**提升模型的推理速度**
	- 场景
		- 对模型的精度要求不高，且需要压缩硬件成本

Ollama 社区上的模型基本都是经过导出量化，所以都是个人用户在用

- 原因
	- Llama-factory 框架的<font color="#c00000">对话模板</font>与**大模型自带的对话模板**是不同的

## 2.1 对话模板
`Tokenizer_config.josn `文件内存在 chat_template 
- 定义角色（系统、用户）
- 定义了生成模型**以何种方式**进行回复
- 不同框架、模型的对话模板**不一致**,各个框架为了高度集成各个模型（集成各个模型的数据处理方式），它定义了一些通用模型的对话模板

## 2.2 解决方法
- vllm 支持使用自定义模板[[【资料】vllm与LMDeploy如何自定义对话模板.pdf]]
- 为了使语言模型支持聊天协议，vLLM 要求模型在其 tokenizer 配置中包含聊天模板。聊天模板是一个 Jinja2 模板，用于指定角色、消息和其他特定于聊天的 token 如何在输入中编码.
	```shell
	vllm serve <model> --chat-template ./path-to-chat-template.jinja
	```

这里的`jinja`文件需要自己生成，生成方式如下：
```python
# mytest.py
import sys
import os

# 将项目根目录添加到 Python 路径
root_dir = os.path.dirname(os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__)))))
sys.path.append(root_dir)

from llamafactory.data.template import TEMPLATES
from transformers import AutoTokenizer

# 1. 初始化分词器（任意支持的分词器均可）
tokenizer = AutoTokenizer.from_pretrained("/root/autodl-tmp/llm/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B")

# 2. 获取模板对象
template_name = "qwen"  # 替换为你需要查看的模板名称
template = TEMPLATES[template_name]

# 3. 修复分词器的 Jinja 模板
template.fix_jinja_template(tokenizer)

# 4. 直接输出模板的 Jinja 格式
print("=" * 40)
print(f"Template [{template_name}] 的 Jinja 格式:")
print("=" * 40)
print(tokenizer.chat_template)
```

# 3 分布式微调
## 3.1 基本概念
- **分布式训练**
	- 单机多卡
	- 多机多卡
- **原因**
	- 模型太大（千亿），卡的性能不够
	- 加速训练过程
- **核心方式**
	- **数据并行**（Data Parallelism）
		-  原理
		  将数据划分为**多个批次**，分发到**不同设备**，每个设备拥有**完整的模型副本**。
		- 挑战
		  **通信开销大**，显存占用高（需存储完整模型参数和优化器状态）
		- 同步方式
		  通过 All-Reduce 操作同步梯度（如 PyTorch 的 DistributedDataParallel）
	- **模型并行**（Model Parallelism）
		- 原理：将模型切分到不同设备（如按层或张量分片）。
		- 类型
		  横向并行（层拆分）：将模型的层分配到不同设备。
		  纵向并行（张量拆分）：如 Megatron-LM 将矩阵乘法分片。
		- 挑战：**设备间通信频繁**，负载均衡需精细设计。
	- **流水线并行**（Pipeline Parallelism）
		- 原理：将模型**按层**划分为多个阶段（stage），**数据分块**后按流水线执行。
		- 优化：**微批次**（Micro-batching）减少**流水线气泡**（Bubble）。
		- 挑战：需平衡阶段划分，避免资源闲置。
	- **混合并行**（3 D 并行）
		- 组合策略：结合数据并行、模型并行、流水线并行，典型应用如训练千亿级模型。
		- 案例：微软 Turing-NLG、Meta 的 LLaMA-2。
## 3.2 deepSpeed 框架 (分布式训练框架)
- 定位：**微软**开源的分布式训练优化框架，支持千亿参数模型训练。
- 核心目标：降低大模型训练成本，提升显存和计算效率。
- 集成生态：与 PyTorch 无缝兼容，支持 Hugging Face Transformers 库。
### 3.2.1 <span style="background:#ff4d4f">核心技术</span>
- ZeRO（Zero Redundancy Optimizer）—— Adam 的改良
	- 原理：通过分片优化器状态、梯度、参数，消除数据并行中的<font color="#c00000">显存冗余</font>。
	- <span style="background:#40a9ff">阶段划分</span>：
		- ZeRO-1：**优化器状态**分片
		- ZeRO-2：**梯度分片** + 优化器状态分片 ——<font color="#00b050">单卡可运行</font>，但是希望<font color="#00b050">多卡加速</font>，模型未拆分，**训练最快**
		- ZeRO-3：**参数分片** + 梯度分片 + 优化器状态分片——<font color="#00b050">解决单卡训练显存不够</font>，模型拆分
	- 优势：**显存占用随设备数线性下降，支持训练更大模型**。
- 显存优化技术
	- 梯度检查点（Activation Checkpointing）：用时间换空间，**减少激活值显存**占用。
	- CPU Offloading：将优化器状态和梯度卸载到 CPU 内存。
	- 混合精度训练：FP 16/BP 16 与动态损失缩放（Loss Scaling）。
- 其他特性
	- 大规模推理支持：模型并行推理（如 ZeRO-Inference）。
	- 自适应通信优化：自动选择最佳通信策略（如 All-Reduce vs. All-Gather）。
### 3.2.2 优势与特点
- 显存效率高：ZeRO-3 可将显存占用<span style="background:#ff4d4f">降低至 1/设备数</span>。
- 易用性强：通过少量代码修改即可应用（如 DeepSpeed 配置 JSON 文件）。
- 扩展性优秀：支持千卡级集群训练。
- 开源社区支持：持续更新，与 Hugging Face 等生态深度集成。

### 3.2.3 使用场景
- 训练百亿/千亿参数模型（如 GPT-3、Turing-NLG）。
- 资源受限环境：单机多卡训练时通过 Offloading 扩展模型规模。
- 快速实验：通过 <span style="background:#affad1">ZeRO-2</span> **加速**中等规模模型训练。

### 3.3.4 模型转换
模型训练后会自动保存成 PTH 模型（例如 iter_2000. Pth ，如果使用了 DeepSpeed，则将会是一个文件夹）
我们需要利用 xtuner convert pth_to_hf 将其转换为 HuggingFace 模型，以便于后续使用
```shell
xtuner convert pth_to_hf ${FINETUNE_CFG} ${PTH_PATH} ${SAVE_PATH} 
# 例如：xtuner convert pth_to_hf internlm2_chat_7b_qlora_custom_sft_e1_copy.py ./iter_2000.pth ./iter_2000_
```

### 3.3.5 模型合并
如果使用了<span style="background:#ff4d4f"> LoRA / QLoRA </span>微调，则模型转换后将得到 <span style="background:#40a9ff">adapter 参数</span>，而并不包含原 LLM 参数
如果期望获得合并后的模型权重（例如用于后续评测），那么可以利用 xtuner convert merge
```shell
xtuner convert merge ${LLM} ${LLM_ADAPTER} ${SAVE_PATH}
# ${LLM}是 baseModel的地址
# ${LLM_ADAPTER} 是转换后的hf模型
# ${SAVE_PATH} 是存储地址
```

# 5. 模型压缩（知识蒸馏）
这最早是为了解决深度学习部署的问题，部署在移动端
- 方法
  - 线性或者非线性量化：1/2bits，int8 和fp16
  - 结构或者非结构性剪枝
  - 知识蒸馏与网络结构简化
## 5.1剪枝
剪枝方法的结构性或者非结构性剪枝，**本质上只是对于模型参数进行mask**（通过矩阵的方式），并不能改变模型的大小，所以它的优势在于：**提升推理性能，但是不能改变模型的大小**

## 5.2 量化
- [ ] 待学习
量化一般指Int8, 但是当前大模型主要用的是Int4
小模型量化不参与训练，但是目前<font color="#2DC26B">大模型是参与训练的</font>。
通过量化+反量化的方式，提升计算速度（计算时使用Int8，权重保存也是Int8），计算完成反量化为FP32
既可以**降低模型的体积又可以提升运算速度**，并且在训练过程中产生，<span style="background:#ff4d4f">结果是可控的，量化后精度损失可以控制在0.1%左右</span>
降低对设备性能的依赖
